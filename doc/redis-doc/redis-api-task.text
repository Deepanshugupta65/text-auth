7. Redis cache key

Because your application has users, we need a different cache for each user.

Use:

cache_key = f"tasks:user:{current_user.id}"

Example:

User 10
↓
tasks:user:10

User 20:

tasks:user:20

So:

Redis
│
├── tasks:user:10
│      └── User 10 tasks
│
├── tasks:user:20
│      └── User 20 tasks
│
└── tasks:user:30
       └── User 30 tasks

This is important for security and correct data isolation.

8. Modify your GET /tasks

At the top of your task router:

import json

from app.db.redis import redis_client

Then your endpoint logic becomes:

@router.get("/tasks")
def get_tasks(
    db: Session = Depends(get_db),
    current_user: User = Depends(get_current_user)
):

    cache_key = f"tasks:user:{current_user.id}"

    # 1. Check Redis
    cached_tasks = redis_client.get(cache_key)

    if cached_tasks:
        return json.loads(cached_tasks)

    # 2. Cache MISS → PostgreSQL
    tasks = db.query(Task).filter(
        Task.owner_id == current_user.id
    ).all()

    # 3. Convert DB objects to JSON-compatible data
    tasks_data = [
        {
            "id": task.id,
            "title": task.title,
            "completed": task.completed
        }
        for task in tasks
    ]

    # 4. Store in Redis for 60 seconds
    redis_client.set(
        cache_key,
        json.dumps(tasks_data),
        ex=60
    )

    # 5. Return response
    return tasks_data
But one warning

Your existing endpoint may already have:

response_model
pagination
filtering
searching
Pydantic response schemas

So don't blindly replace your current endpoint if it has additional logic.

The Redis portion is:

cache_key = f"tasks:user:{current_user.id}"

cached_tasks = redis_client.get(cache_key)

if cached_tasks:
    return json.loads(cached_tasks)

Then after your existing PostgreSQL query:

redis_client.set(
    cache_key,
    json.dumps(tasks_data),
    ex=60
)

10. Add cache invalidation to CREATE

Suppose Redis has:

tasks:user:10
↓
[A, B]

User creates Task C.

PostgreSQL becomes:

[A, B, C]

But Redis still has:

[A, B]

So after creating the task, delete the cache.

After:

db.add(task)
db.commit()
db.refresh(task)

add:

redis_client.delete(
    f"tasks:user:{current_user.id}"
)

Complete concept:

POST /tasks
      ↓
PostgreSQL INSERT
      ↓
Redis DELETE
11. Update task

After your update:

db.commit()
db.refresh(task)

14. TTL

We used:

ex=60

That means:

Cache lifetime = 60 seconds

So:

Redis
┌──────────────────────────┐
│ tasks:user:10            │
│ [A, B]                   │
│                          │
│ TTL = 60 seconds         │
└──────────────────────────┘

After 60 seconds:

tasks:user:10 → ❌

Next request:

Redis MISS
   ↓
PostgreSQL
   ↓
Redis SET again
15. Why both TTL AND invalidation?

This is important.

TTL

Handles cache expiration automatically.

60 sec
 ↓
Cache expires
Invalidation

Immediately removes cache when data changes.

UPDATE
 ↓
DELETE CACHE NOW

So:

TTL = automatic safety
Invalidation = immediate freshness

REDIS IMPLEMENTATION — TEXTAUTH

Redis is used as a cache.
PostgreSQL remains the source of truth.

Docker:
FastAPI → redis:6379
FastAPI → postgres:5432

Redis Python client:
pip install redis

Connection:
app/db/redis.py

Cache key:
tasks:user:{current_user.id}

GET /tasks:
1. Generate cache key
2. Redis GET
3. HIT → return cached data
4. MISS → query PostgreSQL
5. Convert result to JSON
6. Redis SET with TTL
7. Return response

CREATE:
1. Insert into PostgreSQL
2. Commit
3. Delete user's Redis cache

UPDATE:
1. Update PostgreSQL
2. Commit
3. Delete user's Redis cache

DELETE:
1. Delete from PostgreSQL
2. Commit
3. Delete user's Redis cache

TTL:
Cache automatically expires after configured time.

Cache invalidation:
Delete cache immediately when underlying data changes.

Pattern:
Cache-Aside

Redis failure:
PostgreSQL should remain the source of truth.
Cache failure should ideally affect performance, not core data.

That's the complete first implementation. Once you've copied this into your project and it runs, the next thing worth doing is testing Redis properly and adding graceful Redis failure handling—that takes this from a demo cache to a much more production-like implementation.
